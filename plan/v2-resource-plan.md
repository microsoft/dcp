# V2 resource plan

This document tracks the intended direction for DCP V2 resources. The current V2 work establishes the namespace model and the first physical container, image, network, volume, process, and container execution primitives; follow-up work should continue using the design guidelines below so future resources remain consistent.

## Design guidelines

### Namespace model

- V2 resources always belong to a DCP V2 `Namespace`, except for the `Namespace` resource itself.
- V2 resources use standard `metadata.namespace`; controllers use `types.NamespacedName` for normalized references, cache keys, reconciler state, and watches.
- V2 controllers must not perform external side effects when the namespace is missing, terminating, or not active.
- V1 resources remain cluster-scoped and can continue to run without a namespace.

### API layering

- V2 separates physical runtime concerns from logical DCP policy when those concerns have distinct responsibilities or lifecycles. Not every resource requires a physical/logical counterpart.
- V2 physical resources represent backing resources such as containers, images, container networks, volumes, and processes.
- Logical resources represent DCP policy and user-facing behavior such as persistence, reuse, endpoint shape, and higher-level application concepts.
- Shared API fragments that are not specific to V1 or V2 should live in `pkg/commonapi`.
- Container orchestrator packages should not depend on `api/v1` or `api/v2`; API types should be converted at controller or caller boundaries.

### Controller side effects

- Long-running or potentially blocking side effects must run through bounded queued work so reconciliation can record the current state and return quickly.
- Queued action completion should enqueue a follow-up reconcile instead of directly mutating Kubernetes objects from worker code.
- Results from queued runtime work must be applied to controller-owned state as deferred operations during reconciliation, ensuring each reconciliation operates on consistent state.
- Non-idempotent side effects should be guarded by lightweight in-memory data so stale or competing reconciles do not duplicate runtime work.
- DCP does not currently replay controller-owned state after controller crashes; queued side effects that create non-persistent runtime resources must stamp creator and persistence labels so startup harvesting can remove abandoned resources.

### Physical resource ownership

- A `PhysicalContainer` spec sets exactly one of `containerID`, which tracks an existing runtime container, or `container`, which contains the fields used to create one. The mutable `stop` request remains top-level.
- A `PhysicalContainerImage` spec follows the same shape: it sets exactly one of `imageID`, which tracks an existing runtime image, or `image`, which contains the source or target `image`, build, pull-policy, and retry settings.
- Both modes report the observed runtime container ID through `status.containerID`.
- A runtime container supplied through `spec.containerID` is never removed when its `PhysicalContainer` is deleted.
- A runtime container created by the resource is removed on deletion unless `retainRuntimeContainer` is true.
- Creation fails on a runtime name collision unless `replaceExisting` is true. Replacement removes the object that was resolved by name before creating and tracking the new object.
- For physical containers, stop before creation with `replaceExisting` set acquires the existing named runtime through the normal identity tracker and stops it without creating a replacement. A missing target completes stop without creation; lookup errors and tracking conflicts remain retryable. Stop without replacement still skips creation without acquiring a named runtime.
- Higher-level `session`, `persistent`, and `existing` modes remain logical policy. Logical controllers translate those modes into physical creation or reference specifications rather than copying the mode enum onto physical resources.

### Controller-owned in-memory state

- Each resource has at most one controller-owned record representing the latest known state of runtime work that has not yet been fully consumed by reconciliation.
- The record complements resource status and must not become a second, independently observable state machine.
- Controller-owned records must remain minimal: store only values needed to prevent duplicate side effects, correlate runtime events, retain queued-operation results until reconciliation consumes them, or schedule retries. Do not mirror the complete resource spec or status.
- An `applyTo` method may project controller-owned in-memory state onto the resource's status. It must not modify spec or metadata, mutate controller-owned state, schedule work, or perform external side effects.
- State transitions, work scheduling, cleanup, runtime inspection, and controller-owned state updates belong in reconciler or initializer functions.
- When controller-owned state uses a `Ready` condition reason as its current reconciliation state, dispatch reason-specific behavior through an exhaustive initializer map keyed by that reason. Unrecognized reasons must produce explicit invalid-state handling.
- Do not discard an in-memory operation result until its status projection is durable. Use the status-durable callback supplied to `SaveChanges` or `SaveChangesWithDelay` so a failed status write retains the result. If newer state can replace the record before the callback runs, acknowledge the result with an atomic conditional state-map update so a delayed acknowledgement cannot remove that newer state.

### Status and progress reporting

- Public phases describe the coarse lifecycle. In-memory states identify the finer-grained reconciliation action or lifecycle condition, such as copying files, starting, running, or exited. Status projection is keyed by state alone.
- Physical controllers track outstanding asynchronous work with a separate boolean, set when work is queued and cleared when its result is published or enqueueing fails. Runtime observations, dependency availability, retry policy, and operation failures are not progress values; their state transitions and condition diagnostics preserve those distinctions.
- Logical controllers perform synchronous coordination and wait on child watches. They have no asynchronous-work progress field. A retry leaves the current state unchanged; coordination errors, diagnostic conditions, and retry deadlines describe the failed attempt without adding retry states.

- V2 resources should report coarse lifecycle with `status.phase` when a resource has a meaningful lifecycle phase.
- V2 resources should report detailed progress with standardized `Ready` conditions. A condition reason identifies the specific prerequisite, operation, observation, or failure responsible for the current phase.
- Phase communicates broad lifecycle and recoverability; reason must not duplicate generic phase states such as pending or failed. The same specific reason may appear under different phases when the phase distinguishes recoverable from terminal outcomes.
- Condition messages carry instance-specific diagnostics, but consumers should not need to parse a message to determine the cause category.
- V2 status types must not define top-level `status.message` fields. Explanatory and diagnostic text belongs in the message of the condition reporting the corresponding state.
- Controller status helpers should use shared target-first setters such as `setValue(&field, value)` and `setTimestamp(&field, value)`.
- Distinguish recoverable from terminal failures. Status setters return `noChange` when a failure repeats identically, and without a watch subscription or a periodic cache resync that leaves a resource wedged with no pending reconciliation. Recoverable failures should return `additionalReconciliationNeeded` and reconcile at `LongDelay`, matching how V1 paces an unhealthy runtime; terminal failures should not requeue at all. All delays carry jitter, so retrying resources do not poll the runtime in lockstep.

### Type ownership between V1, V2, and orchestrators

- Each API version owns its own resource shapes. `api/v1` and `api/v2` deliberately declare separate copies of container fragments such as `ContainerPort`, `VolumeMount`, `ContainerBuildContext`, and `FileSystemEntry`, so V2 can evolve them without perturbing V1.
- V1 lifecycle keys are gob-encoded from V1 API types, so V1 shapes are effectively frozen. Changing a V1 type name, its exported field list, or its registration order in `initializeLifecycleHashEncoder` invalidates every existing lifecycle key and orphans running containers. `TestContainerSpecLifecycleKeyIsStable` in `api/v1/container_types_test.go` guards all three.
- V2 lifecycle-hash types are appended after the existing V1 entries in the same `initializeLifecycleHashEncoder`; resource-local initializers must not introduce Gob types ahead of that ordered sequence.
- `pkg/commonapi` holds only trivially simple types that are genuinely cross-cutting and are not expected to change, currently `EnvVar`, `Label`, and `PortProtocol`. V1 exposes some of these through type aliases, which preserve gob identity because an alias keeps the underlying type name and fields.
- Container orchestrators (`internal/containers`, `internal/docker`, `internal/podman`) own neutral types in `internal/containers` and must not import `api/v1` or `api/v2`. Conversion from versioned API types to orchestrator types happens at the controller boundary.

### References and watches

- V2 API reference fields use string values formatted as `<name>` or `<namespace>/<name>`.
- Every reference field's doc comment must state explicitly whether cross-namespace references are allowed.
- Controllers normalize references to `types.NamespacedName`.
- Name-only references resolve within the referring resource's namespace. Explicit namespaces must match it unless cross-namespace references are supported.
- Controllers should watch referenced resources and enqueue dependents when updates can unblock reconciliation.
- Watches should use indexes for efficient reverse lookup, for example indexing `spec.imageRef` to find containers referencing an image.

## Current V2 foundation

- `Namespace` defines the namespace boundary for V2 resources and provides namespace-scoped cleanup. Namespace deletion waits for admitted child storage creates to finish, even if their HTTP requests time out, and rejects new creates until cleanup completes. Namespace collection deletion is unsupported. Top-level V2 mutation dry-runs are rejected because the storage backend does not provide no-write dry-run semantics.
- Namespace cleanup ordering and resource selection come solely from relational cleanup metadata. A shared executor resolves each GVR, lists it uncached within the namespace, and issues bounded concurrent deletes; it advances dependencies only after the resources actually disappear.
- `PhysicalContainerImage` provides source image pull and build workflows. The first runtime image ID successfully inspected by the controller is pinned for the resource lifetime and remains the only identity used for later inspection and dependent containers. If that exact image becomes unavailable, the resource reports it unavailable while retaining the published identity and metadata; it never silently pulls or builds a replacement. Delete and recreate the resource to realize a different image.
- `PhysicalContainer` creates or tracks one runtime container, reports runtime status and port mappings, and references same-namespace `PhysicalContainerImage`, `PhysicalContainerVolume`, and `PhysicalContainerNetwork` resources. Container creation waits for every referenced physical resource to become ready. Bind mounts continue to use direct host paths, while named volume mounts resolve the referenced volume's observed runtime ID.
- The one-way container `stop` request completes terminally even when no runtime container was created or started. A stop before creation prevents creation without waiting for prerequisites; an in-flight creation is allowed to settle before stopping its resulting container. Physical containers report `Exited` with `StopRequested` when creation or start is skipped, preserving the raw runtime status when a container exists. Logical containers report `ContainerStopped` and release persistent startup leases.
- A terminal image-acquisition failure terminates backing physical-container startup rather than leaving it Pending. Recreate the container resource to retry startup; making the image available later does not restart a failed container. Logical containers expose that failure and release persistent startup leases without recording nonexistent runtime containers.
- `PhysicalContainerNetwork` creates or references one container network and reports its observed identity, driver, and address allocations. Its spec contains exactly one of top-level `networkID` or nested `network` creation config. Confirmed container network absence reports `Unknown` with `RuntimeNetworkMissing` and stops scheduled inspection retries, matching physical containers; the last identity and details remain available, and another container network with the same name is not adopted. Inspection errors remain retryable. Container networks referenced by ID are always retained. Created container networks are retained when `network.retainRuntimeNetwork` is true; otherwise deletion enumerates running and stopped attachments, forcibly disconnects each container without removing it, and then removes the container network. Name collisions are terminal unless `network.replaceExisting` is true, in which case the controller safely removes the specifically resolved container network before creating its replacement. Container runtime adapters classify their own built-in, non-removable networks, and replacement rejects them before disconnecting any attachments.
- `PhysicalContainerVolume` creates or references one runtime container volume and reports its observed identifier, driver, scope, mount point, and creation time. Its spec contains exactly one of top-level `volumeID` or nested `volume` creation config. Volumes referenced by runtime ID and newly created volumes are retained by default. Setting `volume.removeRuntimeVolumeOnDelete` opts a created volume into controller-managed deletion. Deletion retries non-forced removal until the runtime releases the volume. Removal deliberately does not use force because Podman force-removes attached containers. During namespace deletion, each removable volume retries removal for up to 30 seconds so an externally attached volume cannot block graceful namespace cleanup indefinitely. Name collisions are terminal unless `volume.replaceExisting` is true, in which case the controller safely removes the specifically resolved volume before creating its replacement. Caller-supplied `volume.labels` pass through to created volumes, with reserved persistence, creator-process, and internal resource UID labels set by the controller.
- `PhysicalProcess` launches or references one operating system process and reports its PID, PID-reuse identity timestamp, exit code when available, and lifecycle phase. Its spec contains exactly one of top-level `pid` or nested `process` creation config. Existing processes referenced by PID are observed and always retained when the resource is deleted. Created processes are stopped on deletion and namespace deletion unless `process.retainRuntimeProcess` is true. Deletion never blocks on runtime state: a resource that never took ownership of a running process drops its finalizer without stopping anything. The mutable top-level `stop` request can terminate either mode. Creation supports executable path, arguments, working directory, and environment without importing logical executable or IDE policy.
- The physical resources use coarse public phases, specific `Ready` condition reasons, granular in-memory reconciliation states, and queued work where side effects can block. An outstanding-work boolean tracks only actual asynchronous operations.
- Physical V2 `Reconcile` methods select deletion with a compound deletion-timestamp and in-memory operation guard before finalizer or normal state-machine handling. Deferred results are applied before that guard; normal handlers do not redispatch deletion. Physical image deletion cancels acquisition while its completion is awaited. Logical controllers have no asynchronous operation guard: deletion requests backing deletion immediately, without waiting for child readiness or physical operations to settle first.
- Physical controller management gates initial runtime work on namespace readiness before registering in-memory state; namespace readiness is not a state-machine stage. Normal management owns state updates and status projection, while deletion owns cleanup and persists its final disposition before removing the physical cleanup finalizer. In-flight operations settle during namespace termination, without scheduling subsequent startup work. Logical holds preserve API objects for observation but never block cleanup.
- Created physical containers and processes launch best-effort monitor processes when they are configured to remove or stop their runtime object on Kubernetes resource deletion. Retained physical containers and processes can instead specify a monitor PID and identity timestamp; the retained runtime object is stopped, but not removed, when that process exits. Referenced runtime objects and retained resources without an explicit monitor do not launch cleanup monitors. Abandoned networks and volumes remain eligible for workload-scoped cleanup.

## Follow-up roadmap

### Physical resource layer

1. Migrate V1 container-network tunnel proxy to V2 physical resources.
   - Keep tunnel-specific behavior in the V1 controller, including dcptun image handling, server proxy process management, TLS, tunnel gRPC calls, status, and endpoint projection.
   - Delegate common runtime container lifecycle to V2 physical resources instead of creating and managing the proxy container directly through the orchestrator.

2. Add logical resource controllers.
   - Physical controllers preserve caller-supplied runtime labels and reserve the persistence, creator-process, and internal resource UID labels they need for harvesting and uncertain-create recovery. Controller-set labels override every caller-supplied occurrence of the same key, including logical lifecycle and image build-input labels; unrelated duplicate labels retain last-value-wins semantics.
   - Harvesting normally honors the controller-owned persistence label. Network harvesting is the exception: it intentionally ignores that label and removes orphaned networks after their creator exits so persistent networks cannot exhaust the runtime's finite default network allocations.
   - Build-created images receive persistent, creator-process, and internal UID labels through `build.labels`. Pulling resolves an expected named image and is not a runtime-object creation operation.
   - Logical controllers determine additional labels and physical retention intent when creating physical resources.

### Logical resource layer

After the physical primitives are in place, add logical V2 resources that express user-facing policy on top of physical resources.

1. Add V2 logical container network.
   - `LogicalContainerNetwork` at `logicalcontainernetworks` (short name `lcn`) uses one lifecycle state and state-specific handlers, matching logical containers. After initial namespace admission, Pending resolves policy, acquires the creation lease, performs bounded lookup by container network name, and declares the PhysicalContainerNetwork directly in reconciliation. Creating observes physical API resource identity/readiness; Ready, Failed, and Unknown project subsequent observations. There is no logical work queue, separate progress enum, cancellation operation, or deferred result.
   - Top-level `networkName`, `mode`, and `lifecycleKey` express identity and lifecycle policy. Modes are `session` (default), `persistent`, and `existing`; omit the V1 `persistent` flag and `cleanup` mode.
   - Nested `network` creation configuration contains IPv6 and labels, is required for session/persistent modes, and is forbidden for existing mode. Persistent and existing modes require a container network name; session mode can generate one. The entire spec is immutable.
   - Status exposes coarse phase, readiness conditions, `physicalNetworkRef`, lifecycle key, observed runtime identity, driver, IPv6, subnets, gateways, attached container IDs, and creation time. Readiness requires a current-generation physical observation and completed persistent lease settlement.
   - Owned PhysicalContainerNetworks are created atomically with the logical backing hold and physical cleanup finalizer. The logical hold retains the API object for observation but never blocks backing-resource cleanup. Logical deletion requests API resource deletion, waits for the physical controller to durably project its cleanup disposition and remove its finalizer, settles required retained container network ownership, and releases only its own hold. Deleting PhysicalContainerNetworks are not usable by new dependent containers.
   - The container network lifecycle is independent of container lifetimes. Name lookup, persistent reuse, leases, workload persistence, and harvesting coordination remain logical-controller work; operations on the container network are delegated to `PhysicalContainerNetwork`.
   - `LogicalContainerNetworkSpec.GetLifecycleKey` honors an explicit key or hashes desired IPv6 and stably key-sorted labels using the shared ordered FNV/Gob convention, preserving duplicate-label precedence. V1 and V2 persistent network creation both require an exclusive lease keyed by container network name, including within the same DCP process; the lease protects creation, not the lifetime of references to an existing container network. V1 releases solely through its creation callback scope, not subsequent status changes. Logical networks reuse matching managed container networks and unmanaged container networks, and delegate changed managed container network replacement to the physical controller. Adopted container networks retain their existing labels and lifecycle key.
   - Before container network lookup, the controller attempts startup-harvest protection, matching V1: failed protection delays only reuse of a found container network, not creation of a missing one. Contention uses the ordinary short retry; existing-mode absence retains its monitoring cadence. Verified, template-backed container network ownership is recorded before releasing the creation lease, without waiting for readiness. Ordinary ID-reference adoption releases the lease without registering ownership. Container network selections, generated names, replacement policy, and physical API spec construction are reconciliation-local values; only actual child UIDs, the selected lifecycle key, lease, and retry diagnostics are retained.
   - Physical backing discovery uses an owner-reference index, not a derived backing name. Errors from Create, including AlreadyExists, trigger an uncached owner lookup to confirm a committed declaration. Preserve the selected lifecycle key independently of decoding the child UID so later owner-based discovery does not lose adopted identity. Multiple owned networks fail normal reconciliation, but deletion cleans every owned backing. Cached absence waits for observation; deletion verifies every empty cached list with an uncached owner-filtered namespace list before finalizing, including when no physical UID was recorded.
   - Persistent container network ownership uses the namespace workload ID annotation when present, otherwise the global workload ID. Resolution uses the real namespace reader during lease settlement even when the global default is empty; failures remain visible and retry without releasing the lease. Confirmed container network absence and failed creation supply no ownership candidate. Changed child UID or unauthorized logical-hold removal is terminal during normal reconciliation; neither prevents logical deletion from cleaning currently owned children. Physical API resource deletion settles in-flight work without starting another creation. Logical data is discarded with its finalizer after backing cleanup and lease settlement finish.

2. Add V2 logical container.
   - API types define a namespace-scoped `LogicalContainer` at `logicalcontainers` (short name `lctr`). After namespace admission, one Pending state determines lifecycle policy, looks up any existing runtime container, and declares the appropriate physical backing in the same reconciliation. Creating then observes physical startup until the container becomes Running. Both startup states currently project to the public Pending phase. Subsequent child updates drive runtime observation and cleanup; lifecycle preparation and lookup are not separate reconciliation phases.
   - Watch owned physical containers/images, explicitly referenced physical images/volumes and logical networks, and namespace changes. Reference indexes come from spec, not projected status.
   - Lifecycle preparation, bounded name lookup/inspection, and persistent-store operations run directly in reconciliation. Child updates and explicit reconciliation delays drive progress and retries; there is no logical work queue, cancellation machinery, or deferred operation result. Runtime creation, image acquisition, and other long-running mutations belong to physical controllers.
   - Ordinary child observations and cleanup progression use the controller cache. Cached absence is pending observation, not proof of disappearance; retain the expected identity and requeue. During deletion, every empty cached owner list is verified through an uncached namespace list filtered by controller-owner metadata, regardless of whether the corresponding physical resource UID was recorded. Confirmation failures requeue without finalizing. A successful child Create hands off to child watches rather than forcing immediate observation. Stop and deletion updates arriving during lookup are processed by subsequent reconciliation.
   - Owner-reference indexes discover physical containers and inline images by logical owner UID within the namespace. A single child binds or verifies its recorded UID; multiple children of a kind are terminal during normal reconciliation. Pending acquires both expected child API resources before handing off to Creating, without waiting for image acquisition to finish. State-specific discovery and startup-log projection belong in the state handlers, not shared management. Deletion enumerates and deletes every owned backing, including duplicates and children whose Create response was never recorded.
   - `LogicalContainerSpec.GetLifecycleKey` follows the V1 explicit-key/computed-key contract and FNV/Gob hashing pattern. It hashes the declared configuration and user-supplied build digest without reading Dockerfiles, file secrets, or ambient environment values; archive transport and bytes do not substitute for a supplied digest. Network attachments are excluded because they can be managed dynamically without recreating the container. Stable sorting preserves duplicate environment and label precedence.
   - Session mode creates owned physical resources. Persistent mode acquires the shared runtime-container startup lease, checks a supplied or calculated lifecycle key, reuses a suitable container, or delegates replacement through the physical creation template. Existing mode looks up by runtime name and creates only a physical ID reference, retrying when no runtime container exists unless stop was requested.
   - Physical resources perform all container mutations. The logical controller forwards stop requests, deletes owned physical resources in dependency order, and records persistent workload ownership before releasing the startup lease. Monitors remain creation-only template settings; adoption does not register or upgrade a monitor.
   - Owned physical containers and inline images are created atomically with both their physical cleanup finalizer and the shared logical-backing hold. The hold retains the physical API object until the logical owner observes the final cleanup disposition; it never blocks physical cleanup. External image references are not held.
   - Logical deletion requests backing deletion without waiting for physical readiness. The physical controller settles in-flight work, performs policy-specific cleanup, and durably projects its final outcome before removing its own cleanup finalizer. The logical controller observes that acknowledgment, settles persistence and its startup lease, and releases only its own holds. Retained, owned runtime identities may be recorded; failure, confirmed absence, and ownership conflicts provide no runtime candidate. A changed child UID or unauthorized hold removal is terminal during normal reconciliation; neither prevents deletion from cleaning up all currently owned children.
   - Dependency and creation-retry waits do not prevent cleanup. Deletion never starts another create, replacement, file-copy, or start operation after the current operation settles. Container backings are cleaned up before inline image backings; image deletion cancels acquisition even while the logical hold remains. Logical controller data is discarded with its finalizer after backing cleanup and lease settlement finish.
   - Persistent container ownership uses the namespace workload-ID annotation when present, otherwise the global workload ID. Namespace overrides work even without a global ID; lookup or recording failures remain visible and retain the startup lease for retry.
   - Creating settles workload registration and the creation lease once physical status reports a runtime ID, without waiting for startup readiness. Template/replacement-backed IDs are eligible even when stop is set; ordinary ID-reference adoption and tracking conflicts are excluded. Stop does not remove an entry; cleanup removes stale entries after confirming runtime removal.
   - Reconciliation observes cached backing state, determines logical lifecycle state, applies required changes, and then projects backing details and log sources together. Logical stop intent enters `Stopping` immediately and remains there until exit or terminal failure is observed; it does not wait for a newer physical status generation. Stop writes only set the backing flag to true.
   - Keep only non-derivable lifecycle and operation data in memory. Reference names are projected from observed child metadata and specs, physical runtime details are projected directly, and lease settlement preserves the current reconciliation state and original diagnostics.
   - Runtime lookup results, lifecycle comparisons, generated names, and backing-spec construction are local reconciliation values. Recorded child UIDs and leases remember actual work; child discovery does not depend on prior UID persistence or special creation-uncertainty/release-coordination flags.
   - Errors creating owned physical containers or inline images, including `AlreadyExists`, trigger an immediate uncached owner lookup. A single confirmed child supplies its UID despite the failed Create response; handoff still requires every expected child. Multiple owned children are terminal. Failed lookup retains the API errors and requeues so owner-based discovery can observe the result.
   - Networked creation consumes each nonterminating, nonfailed logical network's published `physicalNetworkRef` to translate references and aliases into `PhysicalContainerConfig.Networks`, without deriving backing names or inspecting physical networks. A missing reference delays declaration; terminal logical-network failure ends preparation. Reference availability is sufficient even while the network is Pending or Unknown. Physical dependency readiness and image-failure handling remain exclusively in the physical container controller. The physical container owns `PhysicalContainerNetworkConnection` requests; the physical network controller owns membership mutations. The logical spec already tracks attachment intent, so no separate logical connection kind is needed. Reusing an existing container does not mutate its attachments.
   - A referenced image, volume, or network observed in `Failed` by the physical container controller ends the current container startup. Replacing the dependency or subsequently setting stop does not clear that failure or initiate replacement-target resolution; the consumer must be recreated. Stop still resolves an existing target while replacement preparation is nonterminal. The logical controller projects the failure and settles its creation lease without workload registration when no runtime container was created. Missing, Pending, and Unknown dependencies remain nonterminal.
   - During preparation, evaluate every dependency reference and collect errors before deciding whether to wait. A pending dependency never prevents observation of a later failed dependency or a lookup error requiring retries, either within a dependency list or across image, volume, and network groups. Logical network resolution checks declarations only; physical controllers retain runtime readiness and image/volume failure handling.
   - Physical container dependency preparation uses shared `Dependencies`, `DependencyLookupFailed`, and terminal `DependencyFailed` states, not per-resource lifecycle states. Corresponding readiness reasons are `DependenciesNotReady`, `DependencyLookupFailed`, and `DependencyFailed`; messages and errors identify the image, volume, or network and preserve its reported failure details.
   - Inline physical image declarations and startup-log projection follow the ordinary Pending preparation flow. Pending does not add image readiness or image-failure guards while waiting for logical network references. Once all required declarations are established, Creating observes the physical container's dependency handling.
   - Terminal preparation failure does not stop independent image acquisition. Continue observing an already-owned inline image and projecting its startup logs through completion, without declaring new backings or resuming container startup; followers opened after acquisition finishes must receive EOF.
   - Top-level `containerName`, `mode`, and `lifecycleKey` express identity and lifecycle policy. Modes are `session` (default), `persistent`, and `existing`; the V1 `cleanup` mode is omitted.
   - A nested `container` configuration is required for session and persistent modes and forbidden for existing mode. Persistent and existing modes require a runtime container name.
   - The container configuration selects exactly one of an `imageRef` to a same-namespace `PhysicalContainerImage` or an `image` pull/build configuration.
   - V2 network attachment configuration uses `networkRef`, consistent with `imageRef` and `volumeRef`, rather than V1's container network `name`.
   - Logical-container attachments reference same-namespace `LogicalContainerNetwork` resources; physical-container attachments reference `PhysicalContainerNetwork`. Separate attachment types keep these reference targets explicit.
   - Spec is immutable except for the one-way `stop` request. Persistent mode can specify a monitor PID and identity timestamp.
   - Status exposes coarse phase, readiness conditions, physical container and image references, observed runtime identity, lifecycle key, timestamps, exit code, and port bindings.
   - Logical V2 kinds use distinct names from V1 kinds, allowing standard API-server registration without introducing conversion or independent-version storage adapters.
   - Provide functionality similar to V1 `Container`.
   - Own policy for persistence, reuse, and higher-level container lifecycle behavior.
   - Delegate concrete runtime work to V2 physical image, container, network, and volume resources.

3. Add V2 logical process.
   - `LogicalProcess` at `logicalprocesses` (short name `lproc`) owns process lifecycle policy; `PhysicalProcess` launches, stops, and observes the process. IDE/debug protocol support remains deferred.
   - Modes are `session` (default), `persistent`, and `existing`, without V1's `cleanup` mode or legacy persistence flag. Session and persistent modes require nested `process` configuration; existing mode requires an explicit PID and identity timestamp and forbids creation configuration.
   - Creation configuration includes executable path, arguments, working directory, environment inheritance, and explicit environment. Both logical and physical process configurations use V2-owned `ambientEnvironment.behavior` with `Inherit` (the default) and `DoNotInherit`, following V1's shape; explicit environment values override inherited values. Lifecycle hashing continues encoding the effective inheritance boolean, preserving computed keys when migrating from `inheritEnvironment`. Persistent mode optionally scopes creation to a monitor PID and identity timestamp. The spec is immutable except for a one-way `stop` request.
   - Lifecycle keys honor explicit values or encode selected process fields and monitor identity individually with the shared ordered FNV/Gob convention, rather than encoding the API configuration struct. Default environment inheritance is normalized. Explicit environment variables use V1's platform-aware last-value-wins normalization before name sorting, so overwritten declarations do not affect reuse; ambient environment values are not hashed. Computed V2 process keys change with this normalization; V1 keys and lifecycle hash type-registration order are unchanged.
   - Persistent store and lease identity is `processes/<namespace>/<name>`, isolating process locks from container and container network keys without sharing cluster-scoped V1 records. Matching live records are adopted, stale records are removed, and changed keys delegate termination of the old identity to an owned `PhysicalProcess` PID reference before launching a replacement.
   - `PhysicalProcess` PID references accept an optional expected identity timestamp; existing logical references and stored process adoption always supply it. Process resolution uses the shared process identity tolerance and reports a mismatched identity as missing without claiming or stopping the reused PID. PID-only `PhysicalProcess` callers retain their existing first-resolution behavior.
   - `PhysicalProcess` launch errors are terminal, matching V1 executable launch and `PhysicalContainer` start behavior. Queueing failures before a launch attempt and observation/cleanup failures retain their separate retry handling.
   - Namespace admission precedes in-memory lifecycle initialization. Lifecycle preparation, stored identity checks, and persistent-record coordination run directly in reconciliation, following the other logical controllers without a lifecycle work queue, cancellation operation, or deferred result. Best-effort output-file removal is submitted to the shared host cleanup queue and does not participate in lifecycle state or lease settlement. Child watches and explicit reconciliation delays drive progress; coordination failures preserve the current lifecycle state and use diagnostic errors and retry deadlines instead of retry states.
   - Logical readiness requires a current-generation `PhysicalProcess` observation and successful ownership recording before startup lease release, including namespace workload overrides with an empty global default. Workload associations are set only for nonempty resolved workload IDs; unscoped reuse preserves an existing owner. Process identity and capture paths are still persisted for reuse without a workload association, and a replacement process does not inherit the retired process's owner. Persistence settlement preserves process reconciliation state and overlays failures in status, following logical containers. Stop requests are forwarded before each ownership-recording attempt, including while persistence is retrying.
   - Owned `PhysicalProcess` resources are created atomically with the shared logical-backing hold and physical cleanup finalizer. Logical deletion requests backing deletion immediately, including during launch or ownership-recording failure, and continues projecting the `PhysicalProcess` log snapshot while cleanup is pending so `LogicalProcess` log followers can drain and release capture readers. The `PhysicalProcess` controller settles outstanding work, cleans up or retains the process, and durably projects its final disposition before removing only its cleanup finalizer. The logical owner then settles persistent registration and its startup lease before releasing its hold, following the other logical controllers without a process-specific handshake.    - Backing handoff observes owned `PhysicalProcess` resources at their stable child names and immediately verifies ambiguous Create outcomes through the uncached reader. Namespace readiness is required only for a new creation; immutable configuration validation excludes `stop`, which is forwarded separately after handoff. Normal observations use cached owner discovery; uncached reads confirm apparent absence. Deletion confirms an absent primary or expected replacement backing uncached, including empty cached owner lists, before settling leases or finalizing. Deletion covers all owned `PhysicalProcess` resources without touching unrelated resources.
   - Disappearance of a handed-off `PhysicalProcess` resource is terminal. The logical resource repeatedly projects completed output for the original backing identity and releases any startup lease without recreating the child or reconstructing process ownership; its deletion remains possible.
   - Status exposes logical phase/readiness, `physicalProcessRef`, lifecycle key, PID/identity, exit code, and finish timestamp. Process details come only from a valid owned `PhysicalProcess`; selected stored identities are cleared after handoff. Namespace cleanup removes `LogicalProcess` resources before `PhysicalProcess` resources.

### Log streaming

Logical and physical containers expose a namespaced `log` subresource at `/apis/{group}/v2/namespaces/{namespace}/{resource}/{name}/log`. Both support `stdout` (the default), `stderr`, and `system`, with follow, timestamps, tail, limit, skip, and line-number options. Logical containers additionally expose image acquisition as `startup_stdout` and `startup_stderr`. Physical images expose pull/build capture as `stdout`/`stderr`, plus their own `system` stream.

Logical and physical container networks expose the same namespaced `log` subresource with `source=system` only. Networks have no stdout, stderr, or startup output; unsupported sources, including the empty/default stdout selection, are rejected before streaming. Each network controller captures its own diagnostics, and an owned physical network also forwards diagnostics to its immediate logical network owner by UID without reading the parent API object. A logical network system stream reads that single resource sink, including diagnostics while Pending or Failed; there is no child endpoint query, proxy, or additional capture layer.

`LogicalProcess` and `PhysicalProcess` resources expose the same namespaced `log` endpoint with `stdout`, `stderr`, and `system`, but no startup/image sources. `PhysicalProcess` resources own their capture files and system diagnostics; owned `PhysicalProcess` diagnostics also flow into the `LogicalProcess` system stream using the same nested resource sinks. Logical reconciliation publishes the output source observed from its backing `PhysicalProcess` as `status.runtimeLogs`. File following, query options, and lifecycle completion reuse the existing shared V2 streamer; no child API lookup or endpoint proxy is involved.

Launched session processes use timestamped capture with a bounded post-exit pipe drain. `LogsComplete` follows output completion after writers close, not root-process disappearance while descendant-held pipes are draining. Retained processes instead inherit direct raw file handles so output does not depend on DCP-owned pipes; the controller closes its copies after launch without closing the child's copies. Retained captures use V1's session-independent persistent output directory, including its `DCP_PERSISTENT_EXECUTABLE_OUTPUT_DIR` override and elevation separation, so session-folder cleanup does not remove live retained output. Their `LogSource.raw` snapshot selects the existing reader's metadata pass-through settings while preserving line filtering. Retained output paths are recorded with persistent process identity, preserved through reuse, and supplied as optional `stdoutFile`/`stderrFile` on identity-bound `PhysicalProcess` PID references. Existing raw captures are read without requiring their filenames to match the adopting resource's identity. Running retained output remains on detach. Retired-output removal is queued after confirming that the process is gone; record retirement and replacement do not wait for removal. The one-shot V2 workload cleanup command attempts recorded-output removal synchronously after confirmed process exit. Output removal uses bounded retries and is best effort, matching V1: failures are logged but do not block resource finalization, process replacement, or retirement of a confirmed-gone process record. `CaptureFile` caches its disposal result, including failure, rather than retrying indefinitely on later close calls. Created and adopted process captures honor `DCP_PRESERVE_EXECUTABLE_LOGS` without changing image-capture preservation policy. Referenced processes without attached capture expose completed empty stdout/stderr while keeping system diagnostics available.

Logical process, physical process, and physical image reconcilers share one host-lifetime output cleanup queue with bounded concurrency, separate from physical launch/stop/acquisition queues. Capture writers close before completion is published; only file disposal is queued. Jobs retain the required capture handles or paths, not controller lifecycle state or leases, and log failures through the base reconciler logger without reopening deleted resources' log streams. Enqueue failures are logged without falling back to inline deletion. Pending work may be dropped when the host lifetime is cancelled, following the existing best-effort queue contract; shutdown does not guarantee draining.

Logical containers, physical containers, and physical images capture resource-specific system diagnostics. Owned physical containers and images also forward diagnostics into their logical owner's stream using scoped nested resource sinks; each resource releases only its own writer. Referencing an independently owned image exposes neither its acquisition output as logical startup logs nor its system diagnostics. That output remains available from the image's own log endpoint. Logical system streams read that single logical stream rather than querying or merging child logs, and can follow diagnostics before runtime creation and after startup failure or runtime exit.

The watch-driven storage and query-option implementation is shared in `internal/logstream`, with version-specific API registration and streamer contracts. V1 keeps its existing API names and startup sources. V2 uses distinct `ResourceLogOptions` and `ResourceLogResponse` kinds to avoid internal-kind collisions when both API versions are registered. Streaming preserves the namespace captured during the API GET handoff.

Each API version registers streamers by resource kind. Logical containers, physical containers, physical images, container networks, and logical/physical processes share one source/session implementation; system-only networks do not allocate runtime capture. A common `LogSource` descriptor carries resource identity, runtime capture ID or pre-captured file paths, availability, and completion. Logical containers publish both `runtimeLogs` and `startupLogs`; logical processes publish only `runtimeLogs`. Reconciliation projects each snapshot directly from the corresponding physical resource. The streamer uses only its watched snapshot and never queries a child resource or proxies a child's log endpoint. Runtime captures are shared by physical resource UID, and availability follows observed runtime startup rather than logical readiness.

Log-source providers expose their primary observed capture through `GetLogSource`. Deletion releases the capture by that source UID, whether it belongs to the resource itself or its backing resource. Logical-container capture cleanup therefore does not rely on a physical-resource watch or the idle scavenger.

Client sessions follow their own API resource's lifecycle. Closing one consumer does not stop another consumer of the same capture. Physical resource deletion ends all consumers of that source, including logical consumers; logical deletion ends its own sessions. Storage preserves the V1 handoff: stop the request-specific watcher when streaming starts and use the existing kind-wide lifecycle callbacks thereafter. V2 callbacks finish sessions on source completion or deletion, not nonterminal snapshot differences, and use the existing final-drain behavior. OpenAPI response schemas remain suppressed because the endpoints return raw text.

The physical image controller captures pull/build output using the shared `internal/logs.CaptureFile` utility also used for V1 container startup. `internal/logstream.LogFileName` names both command and runtime captures from resource identity, source, and an optional capture-instance suffix; physical images use ordinary stdout/stderr names, while V1 startup names remain unchanged. Logical reconciliation observes its owned inline image directly and projects the capture identity, file paths, and completion state, including before container runtime creation. Physical containers do not relay image logs. A single in-memory completion predicate closes capture writers and finishes follows after acquisition succeeds or fails terminally, independently of subsequent image-inspection retries; retryable missing pull results remain open. Adopted runtime containers and never-pulled images with no acquisition output finish without waiting for nonexistent captures. Logical containers with external image references return empty startup logs without waiting for image acquisition.

V2 image acquisition serializes pulls of each image reference through an exclusive state-store lease, including competing resources in the same controller process. Lease keys make an implicit `latest` tag explicit without changing runtime command arguments or assuming registry resolution for short names. Policies are reevaluated after acquisition; `never` only inspects local state and bypasses the lease. Declared build-base pulls use the same path. Docker and Podman capture non-TTY pull output without quiet mode when output is requested; WSLC retains quiet pull formatting. All runtimes resolve pull results using structured image inspection, not progress-output parsing. Freshness policies and persisted pull-history metadata remain deferred.

Image inspections allow three retries at one-second intervals, with consecutive failures tracked in authoritative in-memory data and reset after successful inspection. Exhaustion reports a terminal inspection failure without repeating a completed pull or build. Initial identity verification includes NotFound in that budget to tolerate delayed visibility. NotFound during a missing-policy availability check still permits acquisition immediately, and disappearance of an already verified runtime image retains the existing missing-image behavior rather than reacquiring it.

Runtime adapters resolve a successful pull's identity using the shared resiliency retry strategy established by V1 container inspection: 200ms initial backoff, multiplier 2, 10% jitter, and a six-second retry budget under the caller's context. This includes temporary NotFound responses and retries only inspection, not the completed pull command.

Inspection errors already classified by the orchestrator as runtime-unhealthy leave the retry loop immediately without consuming inspection failures. Image observation reports the existing runtime-unhealthy condition and resumes against the retained selected image ID once the runtime recovers, without restarting a completed pull or build.
