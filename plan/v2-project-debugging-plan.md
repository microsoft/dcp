# V2 Project debugging plan

This document tracks decisions and bounded tasks for extending Project with debug-adapter execution and terminal support. It complements the [V2 resource roadmap](v2-resource-plan.md); it is not approval to implement every task at once or to split/publish a PR stack automatically.

## Current baseline

- [x] Project accepts exactly one process or container launch configuration and directly owns its physical backing.
- [x] Source root is configured independently of execution working directory. It does not implicitly change paths or add source mounts.
- [x] Preparation includes lifecycle projection, stop, deletion, namespace cleanup, owned startup/context logs, and ambiguous container-create recovery.
- [x] Align initial execution with the existing V2 logical lifecycle patterns.

The baseline, host-side `spec.debugAdapter` configuration, and process-based debug subresource/adapter launcher are published in draft PR #350 above services PR #349. Project no longer launches a process application automatically, and a container Project starts only its reusable placeholder context. The draft includes host target tracking, protocol observations, explicit adapter placement, container stdio and container TCP-connect execution. Adapter injection, container TCP-callback and V2 terminal integration are not implemented.

### Delve end-to-end coverage (local)

- `TestV2ProjectDelveEndToEnd` exercises the existing non-terminal host TCP-callback path through a separate production DCP API-server process and real Project controller. A small app under `test/projectdebug`, alongside the shared test tools, is built by `projectdebug-tool` with optimizations/inlining disabled. Its unique source marker selects the breakpoint without hard-coding a line number.
- The scenario initializes DAP, launches the prebuilt binary, waits for `initialized`, sets a verified breakpoint, completes configuration, inspects the stopped stack and local `result=55`, then continues to exit code zero and verifies `Result: 55`. A second case deletes Project while the debuggee is paused. Both verify captured adapter/target identities and confirmed absence after cleanup; no V1 IDE handshake, adapter PTY or container runtime is involved.
- The bounded test client retains interleaved responses/events and reads native DAP framing across WebSocket message boundaries. Synthetic message-order coverage runs locally without Delve. Protocol request payloads and terminal output are not added to resource status.
- Following the PoC, Delve v1.27.2 (compatible with Go 1.27) is registered in `go.mod` as a Go tool, not installed through a separate acquisition path. `cache-delve` resolves/builds it through `go tool -n`, and `projectdebug-tool` builds the native target. `make test-ci` and its Windows PowerShell equivalent prepare both and enable the scenario; ordinary `make test` skips it unless `DCP_TEST_ENABLE_DELVE=true`, which also enables its prerequisites. There is no separate workflow or production adapter-acquisition behavior. The test resolves the registered tool and fails on missing prerequisites when enabled.
- Native compilation, synthetic/client checks and ordinary Project regressions passed. At the user's explicit request, the real host Delve scenario also ran locally on macOS: both continuation/output and deletion-at-breakpoint cases passed, including breakpoint, stack/local inspection and adapter/target cleanup. CI/platform execution remains pending; container and PTY variants remain subsequent coverage. Local E2E execution otherwise remains opt-in under user direction.

### Container TCP-connect adapter execution

- `debugAdapter.tcp.port` configures only the internal container listener for container `tcp-connect`. Omitted TCP options or zero port select 4711; explicit ports are authoritative, range-checked and immutable. Host adapter transport behavior is unchanged, and TCP options are rejected for host placement or stdio. Container TCP-callback remains unsupported.
- Preparation checks the selected internal adapter port against resolved application-port protocols and fails terminally on a TCP collision before creating the backing. UDP may use the same number. The physical container declaration publishes the adapter's TCP listener on host loopback with host port zero; the runtime assigns the exposed port. No service-backed adapter endpoint, host free-port reservation or duplicate publication mechanism is added.
- Project's controller publishes `debugAdapterPort` and `debugAdapterAddress` from its prepared configuration and physical container observation. Ready/prerequisite readiness waits for the runtime host binding. These common fields stay on Project, not adapter entries. The API-server connector watches Project only, tolerates initial endpoint publication, and rejects endpoint drift after acquisition; it never reads physical resources.
- The container adapter receives the internal port through `{{port}}` argument substitution; it must listen on a container-reachable interface supplied by Aspire, not container loopback. DCP connects through the published host address with the existing bounded setup/retry behavior. Adapter stdout/stderr are diagnostics, not DAP or terminal traffic, and no stdin/TTY is allocated for TCP execution.
- Existing Project-UID-scoped provider acquisition shares one exec across pending and established streams, each with its own TCP connection. Releasing one stream does not cancel siblings. Final release settles attached execution; confirmed completion permits a new provider, while unconfirmed termination fences future launches. Failed connection setup after exec preserves the execution in the registry so cleanup uncertainty cannot accidentally allow a second provider. Host PID checks are never applied to container executions.
- Real API/native-socket coverage verifies concurrent opens, independent sibling streams, original internal-port substitution versus host mapping, failed setup, pending endpoint preparation, endpoint changes, confirmed restart and uncertain-cleanup fencing. Running-controller regressions cover default/zero/explicit ports, precreation publication, delayed bindings, TCP collision failure/deletion and UDP coexistence. The conflict regression also covers empty debug-status initialization: the controller may initialize readiness=false without the status wrapper discarding the empty object and blocking finalization.

### Container stdio adapter execution

- Connection establishment returns raw stdio or TCP streams independently of consumption policy. Every acquired connection passes through one shared read-ahead consumer using the buffered pipe with a 64 MiB unread-data limit. Exceeding the limit explicitly fails the session, closes its adapter/client connection, and invokes existing execution release/cleanup. The limit is a generous backlog allowance (eight maximum-sized DAP payloads), not a total-session traffic limit or a guarantee about every adapter workload. Upstream EOF and execution exit independently start the same two-second final-output drain; EOF on one shared-provider connection neither signals provider exit nor stops sibling sessions. Teardown closes the upstream and buffer and joins the read-ahead worker. No disk capture, silent message dropping within a live session, or unbounded forwarding queue is introduced.
- `debugAdapter.placement` explicitly selects host or container execution and defaults to host. Container placement requires a container Project and supports only stdio in this slice. Host adapters remain valid with either Project template; adapter configuration remains immutable. No working-directory/mount defaults, adapter sourcing or terminal options are introduced.
- Project publishes the controller-selected runtime alongside its container ID. The connector consumes only the parent's published context and readiness, pins the runtime/container for its operation, and cancels on parent-reported failure, shutdown, readiness loss or context replacement. It neither validates nor queries the physical backing and requires no published physical-resource UID. Runtime selection uses the published runtime name, never a new auto-discovery decision; prerequisite waiting remains outside the setup timeout.
- `internal/projectdebug` invokes the existing orchestrator exec method directly for one container adapter per stdio session, using caller-owned OS input pipes, bounded fail-on-overflow stdout buffering and separate diagnostic stderr. Only configured adapter environment overrides are passed; host ambient environment is not copied into a container. Prepared container lifetime remains independent of adapter sessions.
- Adapter execution history contains only instance-specific identity, progress and outcomes; shared placement and container/runtime context belong to Project spec/status, not each adapter entry. The runtime pins container identity in memory without inventing a host adapter PID or publishing the runtime CLI's identity. Attached-command completion is distinguished from in-container process termination. Cancellation or an invalid/missing completion result records cleanup unconfirmed; settlement and publication are bounded. Graceful DAP shutdown is attempted before fallback cancellation, and Project retains final container cleanup ownership.
- Process events from container Projects retain container-scoped PIDs and explicitly unconfirmed individual identity/cleanup. They never enter host PID lookup or controller host-process cleanup, even when a host adapter reported them. Repeated unverified PIDs are not treated as identity-safe duplicates.
- Real API/storage regressions cover explicit/default placement, runtime selection, setup expiry/failure, identity replacement before/during exec, raw forwarding, host-placement compatibility, process scope and cleanup uncertainty. Running-controller/native-host coverage verifies prepared context and host-PID isolation. A runtime-gated CI test covers repeated raw stdio sessions inside a prepared container on each enabled runtime; it is compiled but not executed against real runtimes locally. The planned real Delve E2E test remains T10.

### Container duplex-exec foundation

- Shared stream assertions live in `internal/testutil/commandstreams`, imported only by backend test files. The production-reachable simulation helpers remain in `internal/testutil`; their dependency graph excludes `pkg/testutil`, `testify/mock` and `objx`. A dependency-graph test guards this separation.
- `ExecContainerOptions.StdInStream` optionally supplies raw input without changing output-only callers. Docker, Podman and WSLc request `--interactive` only when input is supplied; this does not allocate or prohibit a terminal. Stdin and terminal allocation are independent capabilities, with TTY/PTY execution still deferred.
- Input is a caller-owned `io.Reader`, passed directly to `cmd.Stdin` just as existing orchestrators pass supplied output streams. There is no exec-specific input connector, copier or stream-closing policy in the orchestrators. The owning caller creates and closes long-lived OS pipes, following the host Project adapter pattern; finite readers remain supported. An OS pipe avoids making command completion wait on `exec.Cmd` copying a blocked reader. Existing attached-session cancellation and output-drain guarantees are unchanged, including uncertainty about in-container process termination.
- Native tests redirect only runtime CLI process creation to the shared `delay --echo-stdio` subprocess. All three backends preserve raw binary bytes over multiple exchanges and a payload larger than pipe capacity, keep stderr separate, publish one exit result, support input EOF and leave caller-owned input open after cancellation, child exit or failed launch. No real container runtime is executed locally. The simulated orchestrator also retains caller ownership and excludes live stream handles from recorded invocation snapshots.
- WSLc's separate interactive/TTY exec options were verified against [ContainerExecCommand.cpp](https://github.com/microsoft/WSL/blob/1f3952e5d890d190f975d6f71b4dd25364734d30/src/windows/wslc/commands/ContainerExecCommand.cpp), not inferred from Docker. Actual WSLc execution remains Windows CI coverage.
- This is the shared I/O foundation, not container Project debug admission or adapter-placement API. Project's debug runtime is still host-only. Wiring direct container adapter execution, runtime/container identity binding and container-scoped target observations remains the next Project slice; no host PID interpretation, terminal machinery, adapter sourcing or automatic mounts are introduced here.

### Implemented T6 preparation slice

- `Pending`, container `Creating`, `Ready`, `Active`, `Stopping` and `Stopped` are explicit reconciliation states with state handlers and shared phase projection. `Pending` and `Ready` are public phases; container `Creating` projects Pending. Retry errors overlay status without changing lifecycle state. Namespace admission still precedes initial lifecycle data.
- Pending prepares named ports and one input snapshot. Status publishes `effectiveArgs`, `effectiveEnv` and `launchInputsReady` together, distinguishing empty prepared inputs from unavailable values. Shared V2 evaluation applies only to declared arguments/environment. Process preparation merges evaluated overrides over literal ambient values when inheritance is enabled, with host-specific environment-name comparison and last-value-wins semantics; established DCP/debug-session prefixes are suppressed. Containers never inherit host ambient environment. The prepared controller-owned configuration disables further process inheritance, and Ready does not reevaluate after host environment or service changes.
- Process Projects move directly from Pending to Ready without declaring or starting an application process. Container Projects declare the existing shared-finalizer physical backing with `tail -f /dev/null`, wait for observed running context, and move to Ready while preserving the original application's evaluated arguments separately from placeholder arguments. A generation mismatch does not invalidate an observed runtime state; explicit Stop/deletion intent is handled separately.
- Ready/Active handlers retain prepared context. API-owned active session observations transition Ready to Active; after the last session ends, Active returns to Ready, preserving failed-session history and inputs. These transitions do not select a primary PID or aggregate exit code. The old top-level application PID, identity, process reference and exit-result fields are removed; container identity remains execution-context information.
- Stop and deletion share backing cleanup after bounded debug grace. Stopped retains the prepared snapshot but clears debug prerequisites and completes context capture. Container loss/failure remains a preparation-context failure without automatic replacement or application launch. A placeholder is not an application endpoint; prepared ports/services are retained while endpoint publication waits for the later target/DAP-launch slice.
- Unknown preserves the last observed identity-bound runtime log source, following the logical container/process controllers. Ambiguous discovery or identity/hold changes do not assert capture completion or unavailability. Unknown can refresh a valid original backing's log metadata without reopening its lifecycle; only confirmed backing absence publishes an unavailable/completed source with the original identity, including on retried status writes.
- Failed is terminal and sticky, following the logical container/process terminal handlers. Later backing lookup failures, disappearance, identity changes or ambiguous discovery are logged without replacing the retained phase, reason or message; observable backing/log metadata can still be refreshed.
- Host target registration/cleanup and initialization/launch observations are implemented in the following slices; container adapter execution and terminal target realization remain subsequent T6/T7 work.

### Implemented T6 host target-registration slice

- The API server captures standard DAP `process` events before forwarding them. Each session retains multiple immutable registrations containing a registration ID, diagnostic name, reported PID and captured PID-reuse identity. Repeated reports of one identity within a session are deduplicated; registrations survive session completion and retain separate controller-owned observations. Successful `launch`/`attach` without a reported target, non-local targets, absent PIDs and unavailable identities explicitly report tracking unconfirmed without failing DAP.
- Ordinary status writes preserve API-owned registration/session fields and accept only process observations for matching registration IDs. API-server session completion preserves registrations and controller observations, including when completion uses an older session snapshot. Storage mutations revalidate the Project UID and accept late target reports for existing sessions during stop/deletion; new session admission remains forbidden. Failed publication of a captured handle triggers bounded rollback cleanup rather than silently abandoning it.
- Project observes retained handles independently of session phase through the existing process executor. It never resolves a registered PID again or selects a replacement process. Running, unknown and exited/absent targets do not change prepared Project readiness; no aggregate application PID, exit code or successful-cleanup inference from adapter exit is introduced.
- Stop/deletion schedules a stop-only batch on a bounded WorkQueue with the shared process-stop timeout across the batch. Results return through UID- and operation-scoped deferred operations and remain in controller memory until per-target cleanup observations are durable. Cross-session references to one captured identity share cleanup. A cleanup failure, unobservable target or incomplete descendant cleanup is explicit, never successful cleanup or an indefinite finalizer hold. Deletion retries a prior unconfirmed stop once; late captured targets reopen stopping for their cleanup.
- Existing physical container/image cleanup remains separate and follows target settlement. Finalizer removal retains results until removal is observed, so a failed finalizer write cannot repeat completed target stops. Projects held by unrelated finalizers do not reconstruct completed cleanup or erase its observations. Unconfirmed identities are logged before stop/deletion completes.
- Real API/running-controller regressions use separate shared `delay` subprocesses, not fake API stores or test-binary subprocesses. Coverage includes multiple targets and sessions, disconnect retention, cross-session deduplication, status/finalizer conflicts, namespace termination, identity mismatch, transient observation failure, unconfirmed stop and deletion retry. This is bounded best-effort cleanup of reported local identities, not a guarantee of adapter-reported completeness, recovery across controller restarts, container target tracking, or `runInTerminal` execution.

### Implemented T6 protocol-progress slice

- Each session retains `protocolRequests` for client `initialize`, `launch` and `attach` operations, identified by original client sequence. Each request independently reports Pending, Succeeded, Failed or Interrupted, with response/interruption time and an optional diagnostic message. These are protocol observations, not reconciliation states or target-health claims; no linear DAP initialization/configuration/launch ordering is imposed.
- The shared raw-message bridge observes both directions before forwarding, after translating response correlation to the originating peer's sequence. Unmatched responses still pass through but cannot complete recorded requests; private injected-shutdown replies remain internal. Unknown commands, extension fields, launch arguments and environment remain opaque and are not copied into status. Ordinary `launch.noDebug` follows exactly the same observation path.
- API-server-owned observations survive controller status writes and stale session-lifetime snapshots. Closure interrupts only still-pending requests, preserving completed/rejected outcomes and sibling sessions. Rejection alone does not close the transport, change prepared Project readiness, or claim a target started/stopped. Existing identity capture, cleanup ownership and bounded shutdown remain unchanged.
- Project-specific serving, adapter/provider runtime, status mutation and output handling now live in `internal/projectdebug`, with one exported `Configure` registration entry point called by `internal/apiserver`. API declarations stay in `api/v2`; generic framed mediation stays in `internal/dap`. White-box package tests use public Tilt server startup and real storage/HTTP; production DCP-host behavior remains covered by the real-API/running-controller integration suite. No production exports were added solely for test access.
- Coverage includes out-of-order correlation, initialization/launch rejection and retry, pending attach interrupted by disconnect/stop/deletion, stale/controller updates, sibling session isolation, unknown/private replies, and absence of launch/configuration payloads from retained status. The shared `delay --dap-stdio` fixture provides real subprocess responses; no DAP library dependency or new client protocol is introduced.

The implemented debug slice focuses on process-based Projects. Container differences remain design constraints, not additional implementation scope: retain the prerequisite-ready coordination boundary, separate container startup from application startup, and leave container adapter placement/injection and runtime execution to a later slice. Accepting host adapter configuration on a container Project does not establish runtime debugging support for that Project.

The coordination foundation includes `status.debug` execution/session observation types and an isolated storage update path. Adapter launching and streaming use the separate API-server-owned runtime/connector described below; the storage coordination layer itself does not manage execution.

The production debug connector now uses that foundation at `GET /apis/usvc-dev.developer.microsoft.com/v2/namespaces/{namespace}/projects/{name}/debug`. It accepts a WebSocket upgrade (optionally negotiating `dap`) and forwards native DAP-framed bytes without a DCP handshake or envelope. WebSocket message boundaries do not delimit DAP messages.

### Implemented T5 process slice

- Only process-based Projects with adapter configuration are admitted. Container Projects, unconfigured/stopping/deleting Projects, invalid upgrades, and cross-origin requests fail before adapter launch.
- A pending session is recorded and Project/Namespace watches are established before operation admission. Tilt registers watchers before producing initial snapshots; readiness and subsequent changes are consumed from those watch objects, not repeated storage reads. One startup identity/existence read after registration covers a Project disappearing during subscription and does not select readiness. Waiting is cancellable and outside `connectionTimeout`. Namespace/Project termination, identity replacement, readiness loss, or observation failure ends the request. Adapter setup uses the selected snapshot and watch-canceled context without pre-exec or pre-upgrade record polling; in-flight work settles through existing cleanup.
- Adapter setup uses the declared timeout and completes before upgrade. Failed setup is returned as an API error and retained as session/execution observations, including failures after the setup context expires.
- Stdio and TCP-callback use separate adapter executions per stream. TCP-connect uses one Project-UID-scoped provider with independent connections and reference-counted acquisition/release, including pending requests. Final release stops the provider before another request can reuse its registry slot.
- Shared process execution/exit handlers and process monitors own host execution. Failed host TCP-connect setup retains any started execution for provider release, so unconfirmed cleanup keeps the existing provider fenced rather than allowing a duplicate launch; confirmed cleanup permits a subsequent provider. DAP is never timestamped; network-mode stdout and adapter stderr feed Project-scoped system diagnostics. Ambient DCP/legacy debug-session environment variables are filtered, with explicitly supplied environment entries applied afterward.
- The shared `internal/dap` mediator adopts the PoC's framed messages, serialized per-direction writers, sequence virtualization, and response correlation in both directions. Standard request references (`response.request_seq`, `cancel.arguments.requestId`, and `progressStart.body.requestId`) use the same mapping; progress does not consume an outstanding request's identity. Progress referring to a private injected or unknown request is forwarded without a request association rather than leaking an unrelated wire ID. Cancellation of an unknown/completed request omits the optional request ID, preserving no-op semantics without synthesizing an invalid zero ID. Progress IDs and opaque extension fields remain unchanged, and malformed request references fail explicitly. Messages are limited to 8 MiB, headers to 4 KiB, and outstanding requests to 4096 per direction; fail-on-overflow output buffering replaces the PoC's unbounded queues. No DCP handshake, synthetic application events, or adapter-specific launch interpretation is introduced.
- Client DAP shutdown retains forwarding until adapter EOF, with a two-second post-exit drain bound. A dropped client connection, including a WebSocket close without completed adapter shutdown, fails the session and triggers bounded cleanup. Stdio output buffering does not block the executor's copying goroutine on client consumption; detachment closes the stream, and overflow fails the session independently of forwarding.
- Project stop/deletion is observed through resource watches. Existing `disconnect` requests are tracked; otherwise DCP injects one `disconnect`, consumes its private response, and forwards final adapter messages during a five-second grace. `terminate` does not establish session shutdown: subsequent requests, including client or injected `disconnect`, remain permitted. Grace expiry or rejection is explicit session failure and falls back to bounded execution cleanup. Project deletion defers physical backing teardown until debug observations settle or five seconds from the persisted deletion timestamp elapse; expiry proceeds with cleanup rather than claiming success or waiting indefinitely.
- Unconfirmed adapter termination is reported as failed cleanup without a finish timestamp. A shared provider remains fenced rather than allowing a duplicate launch. Project deletion's bounded grace does not imply confirmed debug cleanup. Adapter exit/results and session failures do not overwrite application phase/readiness or exit code in this attach-focused slice.
- DCP does not advertise or fulfill `runInTerminal` yet; it is forwarded with correlation preserved. The mediator is the foundation for that later interception. Clients use attach configuration for the already-launched application. Deferred application launch and application-result fallback are T6, and terminal execution/interception is T7.

Coverage includes real API/filter-chain tests with executor-boundary adapter simulation for all modes, concurrent provider acquisition, final release and fresh-session restart, fragmented DAP framing and final-output drain, setup/launch failures, pending-request cancellation, parent stop, invalid admission, and server shutdown. Deterministic tests cover partial stdout-write detachment, bidirectional sequence/cancel correlation, private shutdown responses, client-owned shutdown, shutdown rejection and bounded blocked readers/writers. A separate real-API/running-controller integration uses the shared `delay --dap-stdio` subprocess to verify graceful client shutdown, unexpected disconnect, and deletion-triggered shutdown; ordinary `delay` verifies grace expiry for an unresponsive adapter.

Aspire's client must cancel the entire pending HTTP upgrade when the caller cancels, not just its initial TCP dial, and must close the established WebSocket on session cancellation. The pending-cancellation test exercises a real HTTP client abort during prerequisite waiting. The production wire protocol adds no readiness or cancellation messages.

Runtime observation uses one process/container dispatch into typed observation functions, followed by shared identity/error handling, stop forwarding, and phase/log handling. No backend interface or second lifecycle state machine is introduced.

Projects with adapter configuration project controller-owned `status.debug.prerequisitesReady` from Ready/Active after the input snapshot and required execution context are prepared, without application startup. Stop, Project deletion, coordination errors or context readiness loss clear it. False/absent is equivalent. Container context readiness is projected, but the current debug connector still explicitly rejects container debugging until its transport implementation is added. The projection does not start adapters; the connector watches it before setup.

Keeping the container alive also does not override intentional adapter group cleanup: js-debug binder disposal and debugpy launch-session finalization can terminate related targets/sessions.

### vscode-containers launch prior art

Research pinned `microsoft/vscode-containers` at `cb1dcf0a0decced8e7c6f6da477b72dcc531c737`. First-class debugger configuration helpers cover .NET, Node.js and Python; scaffolding for other languages is not equivalent evidence of a complete adapter integration.

- .NET prepares an idle shell container, mounts supplied/acquired vsdbg under `/remote_debugger`, and resolves to coreclr launch with runtime `exec -i` pipeTransport. The C# extension also starts host/workspace-side vsdbg-ui, so this is not evidence that the remote pipe alone is the complete VS Code-facing DAP stack. [Configuration](https://github.com/microsoft/vscode-containers/blob/cb1dcf0a0decced8e7c6f6da477b72dcc531c737/extensions/vscode-containers/src/debugging/netcore/NetCoreDebugHelper.ts#L115-L138), [host descriptor](https://github.com/dotnet/vscode-csharp/blob/9899b6002f809c56aa0373cafe8278e925b60038/src/coreclrDebug/activate.ts#L316-L350).
- Current single-container Python prepares an idle python3 container with the debugger package mounted at `/debugpy`, then executes `python3 /debugpy/adapter` through interactive runtime exec (stdin open, no exec TTY), returning that command as the adapter executable. DAP launch supplies application program/module, arguments, environment and path mappings; internalConsole avoids asking the host to launch a terminal. [Descriptor](https://github.com/microsoft/vscode-containers/blob/cb1dcf0a0decced8e7c6f6da477b72dcc531c737/extensions/vscode-containers/src/debugging/python/PythonContainerDebugAdapterDescriptorFactory.ts#L36-L63), [launch configuration](https://github.com/microsoft/vscode-containers/blob/cb1dcf0a0decced8e7c6f6da477b72dcc531c737/extensions/vscode-containers/src/debugging/python/PythonDebugHelper.ts#L81-L115).
- Node starts the application with an inspector listener in the prelaunch task, then resolves the launch configuration into pwa-node attach from the workspace-side JavaScript adapter. The published inspector port is not DAP. [Task setup](https://github.com/microsoft/vscode-containers/blob/cb1dcf0a0decced8e7c6f6da477b72dcc531c737/extensions/vscode-containers/src/tasks/node/NodeTaskHelper.ts#L129-L159), [attach configuration](https://github.com/microsoft/vscode-containers/blob/cb1dcf0a0decced8e7c6f6da477b72dcc531c737/extensions/vscode-containers/src/debugging/node/NodeDebugHelper.ts#L88-L108).

This substantiates independent container preparation plus per-session adapter exec. It does not settle debugpy child-session endpoint routing: the inspected python-container descriptor always constructs exec, and its handling of child connect configurations was not established. Default vscode-containers cleanup removes debug containers at session boundaries, unlike Project's approved container reuse; that orchestration policy should not be imported. Debugger download/platform selection belongs to Aspire, not DCP. The documented Python Compose attach flow and historical custom-launcher callback are separate topologies, not evidence that a runtime/debuggee port or launcher callback is necessarily client-facing DAP.

## Agreed decisions

| ID | Decision | Consequence |
|----|----------|-------------|
| D1 | Aspire tells DCP which adapter binary to execute and supplies launch inputs. | DCP does not discover, download, or select adapters, or acquire language-specific knowledge. |
| D2 | Adapter execution configuration and DAP configuration are separate layers. | Project describes what to execute; Aspire owns `initialize`, `launch`, `attach`, and their language-specific configuration, subject to the narrow D8 exception. |

### Shared API-owned runtime state

Use one API-server-owned debug execution component shared by subresource handlers. It owns the runtime objects needed by multiple requests; Project's retained execution observations are not the registry from which active providers are reconstructed.

For the existing single adapter configuration per Project, the shared state needs only what concrete launch/connect behavior requires:

- Project UID binding and the current execution identity, including an identity-safe process handle for a DCP-launched provider.
- The resolved TCP endpoint or callback listener, according to transport direction. A callback listener is not interchangeable with an adapter listening endpoint.
- Active/acquiring session references and in-flight startup/shutdown coordination, so concurrent TCP-connect requests share one provider and final release cannot race reuse of a stopping provider.
- Cancellation and owned transport/process resources needed to finish operations and release them on failed acquisition, final release, Project deletion, or API-server shutdown.

Stdio sessions still own separate adapter executions; common bookkeeping does not make their pipes shared. Do not duplicate the full Project spec/status in the registry or persist per-stream ref counts into execution history. Publish execution identity/outcome observations to `status.debug` under D19/D20 for Project coordination, keeping runtime handles, listeners, and references internal.

Use existing synchronization and bounded-work/lifetime primitives rather than holding a registry lock across adapter launch, network I/O, API writes, or cleanup. Retain selected endpoints and identities across ambiguous outcomes; do not allocate a new provider/port merely because a competing request or observation write failed.

### Adapter launch prior art

Re-read PR [#78](https://github.com/microsoft/dcp/pull/78) at head `2d493f4fab40c2f01daeaf158c3efd8df2964661`. `internal/dap/adapter_types.go` defines:

| PoC field | Contract to start from |
|-----------|-----------------------|
| `args` | Command vector: first element is executable, remaining elements are arguments; TCP modes substitute `{{port}}` with the allocated port. |
| `mode` | `stdio` by default, `tcp-connect`, or `tcp-callback`. Validate unsupported values explicitly in V2 rather than copying the PoC's fallback for unrecognized modes. |
| `env` | Explicit adapter environment, adapted to the existing V2/common environment type rather than importing V1. |
| `connectionTimeout` | Adapter transport establishment bound under D28, including shared-provider availability before upgrade; retain the PoC's 10-second default and explicit override. This is not a debug-session duration or DAP initialization deadline. |

`adapter_launcher.go` implements the scenarios:

- `stdio`: launch the command and communicate through its stdin/stdout.
- `tcp-connect`: allocate a loopback port, substitute it into the command, launch the listening adapter, and connect with bounded retries. Additional sessions can use the existing provider address without another process launch.
- `tcp-callback`: bind a loopback listener first, substitute its port into the command, launch the adapter, and accept its outbound DAP connection.
- `ConnectToExistingAdapter`: open another TCP connection to an already-running listening provider. Its use with additional sessions is separate from launching the provider.

The V2 declaration is now available as `spec.debugAdapter` (`api/v2/project_types.go`):

```yaml
spec:
  rootDirectory: /source/application
  process:
    executablePath: /source/application/bin/application
  debugAdapter:
    args: ["/tools/adapter", "--port", "{{port}}"]
    mode: tcp-connect
    env:
      - name: EXAMPLE
        value: value
    connectionTimeout: 10s
```

The declaration alone preserves literal arguments/environment and does not allocate a port or invoke the adapter on create, application startup, or stop. T5 substitutes `{{port}}` in TCP command arguments only when a debug request launches the adapter. The mode defaults to `stdio`; omitted or zero `connectionTimeout` uses 10 seconds. Validation requires a nonblank executable as `args[0]`, rejects unknown transport modes, empty environment names, and negative timeouts, and allows empty subsequent arguments and executable names resolved through PATH. The whole adapter configuration follows Project's existing immutable-spec rule; the one-way Project `stop` request remains allowed.

This supersedes the earlier suggestion to start with only a caller-supplied static TCP endpoint and defer port allocation. Do not add working-directory, endpoint-discovery, or transport-policy fields absent from this contract without a concrete need. Reuse existing V2/shared execution and networking primitives when implementing allocation, cancellation, output diagnostics, and process cleanup.

TCP callback direction needs explicit verification for concurrent streams: the callback listener belongs to DCP, not to a listening adapter provider. The returned callback address cannot simply be treated as an adapter listening endpoint for `ConnectToExistingAdapter`. Determine how a callback-mode adapter establishes additional connections before promising the same sharing mechanism as TCP-connect; do not solve that gap with a speculative public protocol.

#### TCP-callback reuse finding

The PoC does not establish correct shared-provider reuse for callback mode:

- `adapter_launcher.go:200-212,275-305` binds a DCP listener, accepts one outbound adapter connection, and sets `adapter.Address` to that DCP listener address.
- `bridge_manager.go:668-676` treats both TCP modes alike for child sessions and passes this address to `runWithConnectionAndAdapter`.
- `bridge.go:175-191` calls `ConnectToExistingAdapter`; `adapter_launcher.go:418-425` dials the supplied address. For callback mode, that dials DCP, not an adapter listener. The launcher has no continuing accept/forwarding path that connects this new socket to the original adapter.
- `adapter_launcher_test.go` tests connecting to an existing listening adapter, environment filtering, and an address field; it does not verify callback-mode additional sessions.

This is a verified source-level prior-art bug, not behavior to port into V2. Shared registry/port retention does not change connection direction or create a way to request an additional outbound callback. D29 resolves the implementation policy: each callback stream launches its own adapter/listener. Do not dial the DCP callback listener as an adapter endpoint; only TCP-connect uses a shared listening provider.

Failed-launch reporting is a justified proposed extension so Project can report launch failure in addition to the pre-upgrade HTTP error. Use the existing V2 phase/Ready-condition pattern rather than overloading an exit code or adding an unstructured top-level error/message:

### Proposed minimal session observations

Add `status.debug.sessions`, keyed by an API-server-assigned session `id`, alongside `executions`. Proposed fields:

| Field | Purpose |
|-------|---------|
| `id` | Correlate this subresource stream, its lifecycle observations, and later terminal-target requests. |

| `conditions` | Standard reason/message reporting for setup/connect/transport failures without conflating them with the application result. |

Derive live-session count from `Running` entries and show pending/failed entries separately; do not persist redundant counters that can diverge. Execution failure and individual connection failure are different observations: a failed connection does not necessarily mean the shared adapter process exited. Successful DAP forwarding also does not imply a successful application launch.

Session-history retention is approved under D27: retain entries until Project deletion and update their lifecycle observations in place, matching execution history.

For `runInTerminal`, coordinate creation with Project through API updates:

1. The handler receives the reverse request and publishes its required launch inputs with a stable request ID, originating session ID, and parent UID binding. 2. Project reconciliation consumes the request and creates/adopts the appropriate Project-owned physical target through its normal lifecycle machinery. 3. Project publishes a controller-owned realization outcome: pending, backing reference/identity, or launch failure, with the information needed for the DAP response. API-server request/session updates must not overwrite this outcome, and controller updates must not overwrite their inputs.
4. The handler observes the outcome and answers the originating reverse DAP request. Creating the API object alone is not proof that the target started; use the physical execution's current observation and valid process information. A host runtime CLI PID is not an in-container target PID.
5. Subsequent target status and terminal information come from the physical backing, projected as needed by Project. Session association expresses provenance, not a cleanup scope that kills the target on stream closure.

Avoid copying full target status into both session and application sections. Resolve exact request/outcome fields and placement, multiple targets per session, and result authority in T7. D26 cancels unstarted requests on disconnect and requires in-progress/ambiguous realization to settle without treating closure as target termination. Define an identity-safe admission/cancellation boundary using resource updates, not independent stale observations. This is internal API-resource coordination, not a new public DAP handshake or child-session control protocol.

### Minimal debug-subresource contract

An explicit debug-subresource request launches a configured adapter or connects to a reusable provider and connects the client to that session's DAP transport. Aspire sends DAP requests and receives responses/events using the protocol's native framing; DCP forwards them, apart from the agreed `initialize` and `runInTerminal` handling.

The request already identifies the namespace, parent Project, and requested debug action through the DCP API. Resolve and bind it to the current parent UID using the normal API/resource-lifecycle checks; do not ask the client to identify the same Project again through an in-stream handshake. This removes the side-channel rendezvous that motivated extra token/session handshakes in the V1 IDE-based proof of concept. It does not replace applicable API access checks or the need to reject stale/deleting resources and conflicting session requests.

The API transport still needs to support bidirectional traffic, cancellation, backpressure, and explicit failures. Those are transport and resource-lifecycle obligations, not reasons to introduce another application control protocol. Use normal API/transport errors before streaming and define stream termination behavior without inventing custom control messages by default.

#### Connection establishment and adapter readiness

Opening a connector subresource is an HTTP operation, not creation of a persisted debug object followed by automatic stream creation. Kubernetes invokes `Connect` and then its returned handler; that handler controls when to perform the WebSocket upgrade. Adapter preparation can therefore precede the upgrade.

Project execution-prerequisite readiness is distinct from adapter transport readiness and application readiness. For example, a container must be running and have completed required pre-start resource injection before an operation can execute inside it, but a deferred debug target need not already be running. Gating deferred debugging on the application's generic `Ready` condition could deadlock its launch.

Under D32, use `status.debug.prerequisitesReady` rather than another condition state machine. Project reconciliation owns this field and validates the backing's current availability; the API server continues to own `debug.sessions` and `debug.executions`. The connector consumes the published container ID/runtime and parent readiness without duplicating backing validation or querying physical resources.

Wait for this prerequisite projection using the request/server lifetime and resource watches, outside the adapter connection timeout. Client cancellation, Project deletion, namespace termination, and terminal prerequisite failure must end the wait explicitly; do not interpret the absence of an adapter timeout as permission to leave orphaned requests. Start `connectionTimeout` only when adapter/provider setup begins. No separate prerequisite timeout is selected.

Coordination: Project reconciliation publishes prepared execution context and readiness through controller-owned status. The debug handler observes the parent through API reads/watches, binds to its UID and supplied container ID/runtime, and checks parent readiness before execution and upgrade. It does not validate the physical backing. Readiness loss before launch must not retarget an existing request; deletion, replacement, and parent-reported failure need explicit outcomes. A readiness projection is not a reservation: cancellation and races still require identity-safe operation handling.

Prefer extending the existing Project projection where it already expresses these prerequisites. Add a separate condition/context only where deferred/container behavior demonstrably cannot use existing fields; do not add a generic request/acknowledgement protocol by default. Host-side adapter setup should wait only for prerequisites it actually requires, not automatically require an application container merely because Project declares one.

Proposed initial ordering, pending implementation verification:

1. Validate parent/namespace identity and the requested WebSocket upgrade before launching anything.
2. Acquire session/provider ownership and perform bounded, cancellable adapter launch or provider startup/connect.
3. Once the adapter-side transport is established, return the WebSocket upgrade (`101 Switching Protocols`). Aspire can then send native DAP, including `initialize`, immediately.
4. If setup fails before upgrade, return a normal HTTP/API error instead of establishing a stream that needs a custom failure handshake. Release all acquired references and stop any newly owned execution as appropriate, including when launch succeeded but upgrade failed or the client disappeared.
5. After upgrade, use the stream's normal failure/close behavior for transport or adapter failure; the selected API state surface carries any additional execution diagnostics.

Transport establishment does not prove successful DAP initialization or target launch. A stdio adapter may have a running process and connected pipes but still exit immediately or reject `initialize`; a network connection may be accepted before protocol initialization completes. Aspire still owns DAP initialization and its responses. Do not wait for a DAP `initialized` event before opening the stream: many adapters need client requests first.

Only introduce an explicit in-stream readiness/failure exchange if implementation evidence shows preparation cannot be bounded or completed before upgrade, or a concrete client requirement needs early stream establishment. Verify HTTP/client/proxy setup timeouts and cleanup races before adopting the proposed ordering; do not add a speculative handshake merely because launch is asynchronous.

Timeout fact-finding confirms that the current tilt/DCP server does not impose a fixed adapter-setup timeout on a correctly classified long-running connector, including before WebSocket upgrade:

| Setting/path | Current behavior | Effect on debug setup |

Evidence: the duplex probe now deliberately delays inside `Connect` for 500 ms with `RequestTimeout` set to 250 ms. The long-running connector still upgrades and exchanges DAP bytes; an otherwise identical connector omitted from the long-running set returns a timeout before upgrade. Conclusion: prepare-before-upgrade is feasible without a readiness handshake or tilt change. D28 selects `connectionTimeout`, defaulting to 10 seconds with an override, for adapter transport setup; Aspire can configure its connection/upgrade wait to accommodate it. External proxy limits remain deployment-specific and do not change the verified direct-server behavior.

Session shutdown gives the adapter an opportunity to release its resources and terminates that adapter session. The adapter may terminate the application as part of shutdown, gracefully or otherwise; DCP does not guarantee application survival. Conversely, session closure does not guarantee application cleanup: any application left running remains Project's responsibility, including targets launched through `runInTerminal` that are not OS descendants of the adapter. Project stop/deletion and namespace cleanup ensure final target termination and descendant cleanup. Reuse existing execution/cleanup primitives where applicable; selective adapter-only process termination is not a prerequisite solely to guarantee survival. Killing a host runtime CLI still does not establish what happened inside a container.

Multiple active sessions may have distinct adapter processes or separate DAP connections to one provider, according to the same Project-declared adapter configuration. Closing one must not close other sessions or kill their provider. A reverse DAP request for child debugging remains client-coordinated: Aspire receives it, opens a second debug stream on the same Project, and sends the corresponding initialization/launch configuration. Reuse the adapter execution/connection configuration, not necessarily the original DAP launch arguments: Aspire supplies the DAP configuration requested for the additional launch. DCP does not need to correlate the streams into a parent/child debug-session hierarchy or add a child-launch endpoint, handshake, or language-specific fork policy.

| Declared DAP transport | First debug stream | Additional debug streams | Stream closure |
|------------------------|--------------------|--------------------------|----------------|
| Stdio | Launch the configured adapter and forward its dedicated DAP stdin/stdout. | Launch another adapter process with the same configuration and independent pipes. | Terminate that stream's adapter; observe application effects without assuming either cleanup or survival. |
| TCP-connect | Connect to the resolved provider endpoint once available; launch a DCP-owned provider on explicit demand when necessary. | Acquire a reference and connect again to the same provider; do not relaunch it or share another stream's connection. | Release that session's reference. Stop a DCP-owned provider after the final reference is released, never while another session uses it. |
| TCP-callback | Bind a DCP listener, pass its allocated port to the launched adapter, and accept the outbound adapter connection. | Launch a separate adapter with its own listener and allocated port, using the same declared configuration. | Terminate that stream's adapter and close its connection/listener; do not affect another callback session. |

Provider acquisition/release must account for in-flight session admission and failed connections, not just count established sockets. A failed launch or connection releases its acquired reference. When a new request races the final release, settle shutdown before launching/reusing a provider; never attach to a stopping process or duplicate startup. Use controller-owned identity and existing bounded-work/deferred-result patterns rather than a new client-visible ref-count protocol.

Adapter/session state and evaluated launch inputs may need an API representation, but neither requirement automatically belongs inside the DAP stream. First assess existing resource/status and subresource mechanisms. Keep their exact representation open until a concrete consumer need establishes the minimum necessary addition.

### API-server/controller ownership: design A selected

The API server and controllers run in separate processes. Design A is selected because resource updates already provide controller coordination without another internal channel. The comparison below records the considered alternative and the selected design's obligations; it is not an outstanding architecture choice.

| Concern | A: API server owns the debug subresource experience | B: Controller-side execution via an internal channel |
|---------|--------------------------------------------------|----------------------------------------------------|
| Execution and data path | API server owns adapter launch/connect, per-stream I/O, and shared-provider lifetime. DAP stays within the handler/adapter path. | API server handles the external upgrade and relays to controller-side execution. An internal duplex channel carries adapter traffic and associated lifecycle coordination. |
| Project coordination | All communication with the Project controller is through API resource updates observed by reconciliation. Define ownership of those updates without competing status writers or using projected status as controller authority. | Internal requests/results communicate session admission, execution identity, and cancellation; Project reconciliation remains authoritative for its lifecycle and projects API status. Exact placement of session bookkeeping still needs design. |
| Main advantage | No internal streaming service or additional process-to-process connection to establish and secure. Stream disconnect is directly observable by the adapter owner. | Keeps execution and application cleanup close to existing physical controllers/executors; runtime handles and operation results need not be transferred through API fields merely to coordinate processes. |
| Main cost | Runtime ownership spans server-owned adapters and controller-owned applications. Must reuse shared execution primitives without duplicating a controller lifecycle, and make identity/result/cleanup handoff through asynchronous API writes reliable. API server needs any executor/runtime access required by the approved scope. | Requires internal transport discovery/access control, UID-scoped admission, relay backpressure, cancellation and teardown, and explicit behavior when either process or the connection exits. Avoid a second independently authoritative session state machine. |
| Failure paths to prove | Stream closes before an API update succeeds; parent changes/deletes before the controller observes a launched target; status/write conflicts; provider acquisition races; API server exits while execution/cleanup is outstanding. | Disconnect races internal launch admission/results; internal connection fails after launch succeeds; stale/replaced Project identity; provider acquisition races; either process exits while the other still owns resources. |

Neither design sends DAP messages through Kubernetes resource updates. Resource updates express the necessary coordination state, identities, and results, not a polled byte stream or message queue. Both must use existing identity-safe execution and cleanup primitives, preserve Project's responsibility for remaining applications, and respect the unsupported-controller-restart boundary.

Design A deliberately places debug execution under API-server ownership while reusing shared execution primitives; it must not duplicate a controller lifecycle inside a generic HTTP handler. Design B is not planned.

The parent storage provider supports `rest.StandardStorage`, including updates and watches, rather than read-only observation. Successful validated storage updates publish watch events that can trigger Project reconciliation. No API client is automatically injected into a subresource, but one can be explicitly wired if needed. The normal parent update strategy preserves status; status storage is separate. Direct storage calls also do not automatically traverse HTTP authorization/admission or DCP's separately applied namespace-lifecycle wrappers. Choose the smallest coordination surface and update path that preserves these checks, resource-version/UID safety, and writer ownership; do not use arbitrary controller-owned status fields as an API-server command channel.

D19 selects a dedicated Project section for debug coordination, not separate debug-execution resources. With D32, ownership is field-scoped: the API server owns session/execution observations and the controller owns `prerequisitesReady`. Each update path must preserve the other writer's fields and sibling entries. The reconciler consumes externally owned observations, never its own unified status or readiness projection as lifecycle authority. Preserve observations needed for result projection or application cleanup until the consumer has safely accounted for them; an ended stream alone is not permission to erase its target identity or completion result.

### Direction requiring verification

Verified Delve terminal topology for T8: the user's interpretation matches VS Code Go's integrated/external-terminal launch path. Inspected vscode-go `1608cb5c907bfb238967d9aceb507620b08cf2a3` and Delve `749588dac9874b39e50b4c168f9ec064a4ddfad1`, and cross-checked the relevant behavior in released vscode-go v0.58.0 and Delve v1.27.2.

- VS Code Go's wrapper, not Delve's target-launch handler, emits `runInTerminal` to launch **Delve itself**. It first creates a DAP rendezvous listener, adds `dlv dap --client-addr=...`, requests integrated/external terminal execution of that command, then carries DAP over the returned TCP socket. Current main explicitly uses loopback; the released extension has the same callback topology with different address construction. An explicitly supplied adapter port bypasses this extension-owned launch path. [Selection](https://github.com/golang/vscode-go/blob/1608cb5c907bfb238967d9aceb507620b08cf2a3/extension/src/goDebugFactory.ts#L376-L405), [terminal launch](https://github.com/golang/vscode-go/blob/1608cb5c907bfb238967d9aceb507620b08cf2a3/extension/src/goDebugFactory.ts#L409-L456).
- `dlv dap` uses a network connection, not stdin/stdout DAP. TCP is the VS Code path, but "always TCP" is too strong: Delve also supports `unix:` listeners/callback addresses. DAP startup sets `Debugger.Foreground=true`; its CLI does not expose the separate `--tty` target option offered by `dlv debug`/`dlv exec`. [DAP CLI/startup](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/cmd/dlv/cmds/commands.go#L220-L252), [foreground](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/cmd/dlv/cmds/commands.go#L588-L609), [network selection](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/cmd/dlv/cmds/commands.go#L1262-L1276).
- For a launched target, default/local output and no explicit redirects inherit Delve's stdin/stdout/stderr. Native Linux launch also handles foreground process-group/TTY ownership; Windows native launch passes the selected standard handles; macOS's LLDB path has its own terminal/foreground handling. `noDebug` likewise defaults to Delve's standard streams. This is inheritance at process launch, not terminal traffic carried inside DAP. [Native defaults](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/pkg/proc/native/proc.go#L440-L486), [Linux launch](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/pkg/proc/native/proc_linux.go#L65-L118), [noDebug](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/service/dap/server.go#L1417-L1467).
- This is not a universal PTY requirement for Delve. Ordinary non-interactive debugging works without a terminal. `stdinFrom`, `stdoutTo` and `stderrTo` provide file redirection, and `outputMode=remote` redirects target stdout/stderr into DAP output events rather than inheriting those streams. Remote output does not provide an interactive terminal-input protocol. Attaching to an existing target does not change that target's terminal. [Launch redirection](https://github.com/go-delve/delve/blob/749588dac9874b39e50b4c168f9ec064a4ddfad1/service/dap/server.go#L1231-L1338), [VS Code stdin guidance](https://github.com/golang/vscode-go/blob/1608cb5c907bfb238967d9aceb507620b08cf2a3/docs/debugging.md#L577-L594).

Implementation consequence: a generic adapter-terminal capability paired with TCP-connect/TCP-callback is needed to reproduce this launched-target terminal experience; target `runInTerminal` handling alone does not reproduce it. Keep DAP bytes separate from the adapter PTY, and exercise target stdin plus terminal behavior through a PTY-launched Delve in T10 CI coverage. Aspire supplies the launch arguments; do not hard-code Delve behavior into DCP. This source verification does not substitute for platform/runtime execution coverage.

Confirmed dependency: when Delve runs inside the Project container and a target terminal is desired, adapter-terminal execution (T8) depends specifically on container **exec** PTY support (the exec path of T3), not primary-container attach or raw `exec -i` pipes. That exec terminal carries Delve/debuggee terminal I/O and resize; DAP remains on its separate reachable network transport. Host Delve terminal execution instead depends on host-process PTY support (T2). Non-terminal Delve operation does not acquire these terminal prerequisites.

As part of T8, add an explicit adapter-configuration field requesting a PTY for the adapter itself, independently of target `runInTerminal` behavior. Reject that option with `mode=stdio`, including omitted mode (which defaults to stdio); adapter PTY I/O must remain separate from TCP DAP. Implement the field and its execution/terminal ownership together with the applicable T2/T3 support rather than accepting an ignored option beforehand. The exact field name remains to be selected.

The client scenario motivating concurrent sessions includes JavaScript child/fork debugging: an adapter can request an additional debug session, and the client may connect to the same provider port with a fresh DAP initialization/launch flow rather than start another provider process. Verify exact reverse-request and connection behavior against the chosen adapter before implementing compatibility coverage; do not hard-code JavaScript behavior into DCP.

Adapter-terminal I/O and target-terminal I/O are distinct. DAP bytes must remain separate from terminal output, terminal framing, and timestamped logs. The supported transport for a PTY-backed adapter must be verified before choosing its launch configuration.

## Lifecycle and implementation guardrails

- Follow parent V2 logical and physical controller patterns first: explicit single-state dispatch, deletion request before normal dispatch, and explicit invalid-state handling.
- Controller-owned state is authoritative and minimal; status is projection-only. Existing physical resources retain their execution ownership. Under D18, the API server owns debug execution using shared primitives and publishes explicitly owned coordination updates; Project reconciliation consumes them without treating its own projected status as authoritative. Avoid duplicate lifecycle machinery and competing writers.
- Queue blocking side effects through bounded work; apply UID-/operation-scoped deferred results during reconciliation. Settle in-flight operations before releasing ownership or finalizers.
- Inspect/adopt prior successful creates before retrying or reevaluating prerequisites. If absence is confirmed, revalidate selected prerequisites without changing pinned identities.
- Distinguish a live debug connection, adapter runtime lifetime, target runtime lifetime, and outstanding launch/stop work. A disconnected stream must not implicitly determine all four lifetimes.
- Use relational namespace-cleanup metadata and existing finalizer/cleanup machinery. Preserve result and capture completion through status conflicts.
- Keep read-only log streaming and duplex DAP/terminal transports separate. Reuse owner-scoped system diagnostics and immediate source snapshots; no child-log endpoint proxy or parallel lifecycle callback path.
- Start with native DAP forwarding. Do not add generic session-management RPCs, custom handshakes/envelopes, or speculative configuration for future capabilities.
- Never use DAP traffic or adapter configuration as an excuse to restore V1 IDE protocol orchestration, language-specific launch policy, or controller-restart recovery.

- [ ] Concurrent child/fork sessions work with distinct adapters and multiple connections to one provider; one session closing does not terminate siblings, their provider, or the Project application.
- [ ] Each stdio/TCP-callback stream launches its own adapter (and callback listener where applicable); each TCP-connect stream connects independently to the same provider endpoint without spawning another provider, including concurrent opens.
- [ ] Different debug-subresource handler instances share the resolved provider endpoint and acquisition state for the same Project UID; a same-name replacement Project cannot reuse the old registry entry.
- [ ] A DCP-owned provider stops after final session release; failed/pending connections do not leak references, concurrent acquire/release cannot duplicate or reuse a stopping provider, and externally owned provider processes are left intact.
- [ ] Reverse requests for additional sessions reach Aspire, which opens a second debug stream on the same Project using the same adapter execution/connection configuration and supplies the requested DAP configuration, without a per-child adapter override or DCP session-hierarchy protocol.
- [ ] Host and container adapter execution; injection completes before container start.
- [ ] Immediate execution followed by attach: no application restart; adapter exit leaves a live application running.
- [ ] Deferred execution: no early normal launch or duplicate target; container bootstrap remains distinct from application readiness.
- [ ] Debug operations wait for their actual Project execution prerequisites, consume controller-published backing identity, and handle readiness loss/deletion/replacement without duplicate launch, retargeting, or waiting for an application whose launch requires the debug session.
- [ ] Prerequisite waiting does not consume `connectionTimeout`; controller readiness updates preserve session/execution history, API-owned updates preserve readiness, and loss of a running container clears readiness.
- [ ] Aspire can read required resolved inputs before its DAP configuration, bound to the intended Project/physical identity, without assuming an extra in-stream setup protocol.
- [ ] Native DAP clients can use the stream without a DCP-specific handshake, envelope, or preamble.
- [ ] Adapter-side transport is established before successful upgrade; pre-upgrade launch/connect failures return API errors, and cancelled setup or failed upgrade releases executions/references. DAP initialization still occurs over the established stream.
- [ ] Partial DAP frames, concurrent requests/events, reverse-request correlation, backpressure, transport errors, and cancellation.
- [ ] `initialize` capability handling and `runInTerminal` success/failure responses without taking over other DAP configuration.
- [ ] PTY input/output/resize, reconnect policy, output drain, and cleanup for host targets, in-container targets, and adapter terminals as supported.
- [ ] Application exits before adapter, adapter exits before independently observable application, and adapter-only fallback; known exit code zero is not confused with unknown.
- [ ] Failed adapter launch, failed target launch, never-created backing, missing/replaced backing, and ambiguous creation responses.
- [ ] Stop/delete/namespace cleanup during preparation, adapter launch, reverse-request target launch, active streaming, and completion; no leaked process, terminal, listener, or capture.
- [ ] Status conflicts preserve selected identity, execution result precedence, and follower completion.
- [ ] API-server debug-observation updates and controller unified-status updates preserve one another; concurrent streams cannot overwrite sibling entries, and observations needed for cleanup/results survive stream closure and write conflicts.
- [ ] Execution history retains running/completed/failed-launch entries until Project deletion, without duplicate failure entries on write retry, invented PIDs/exit codes for failed launches, or adapter errors falsely completing a live application.
- [ ] Session status independently distinguishes pending/live/closed/failed streams and shared provider execution; counts derived from observations agree with reported session phases without becoming runtime reference counts.
- [ ] Each `runInTerminal` target is associated with its requesting session for reporting, including multiple requests and targets surviving session closure, while Project retains cleanup/result responsibility.
- [ ] Parent-mediated terminal launch requests survive observation/write conflicts and ambiguous physical creates without duplicate targets; reverse responses wait for actual launch outcomes and pending-request disconnect behavior follows the approved policy.
- [ ] Platform/runtime behavior is exercised in CI; do not run local real-runtime/E2E suites.
- [ ] A real Delve E2E test, analogous to the PoC's adapter test, verifies V2 initialization/launch, breakpoint handling, stack/variable inspection, continuation and cleanup in CI (T10).

Use the real API server and running controllers for resource behavior tests, with fault injection only at executor/orchestrator/API-operation boundaries. Shared protocol/terminal utilities also need focused unit coverage. Run race detection for synchronization changes.
